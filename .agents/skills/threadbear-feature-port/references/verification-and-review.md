# 検証マトリクス・証拠レベル・独立レビュー手順

「テストが通ったのに実機で別物だった」「見た目だけ確認して確定後のフローが抜けていた」を防ぐための検証・監査基準。

---

## 1. 証拠の6段階と格上げ禁止ルール

検証結果は必ず以下のレベルで記録し、**下位レベルの成功を上位レベルの完了証拠に格上げしない**。

| Level | 証拠の種類 | 保証できること | 保証できないこと（混同禁止） |
|---|---|---|---|
| **L1** | 静的確認（コード読解・型・lint・差分照合） | 配線・型整合・禁止パターンの有無 | 実際の描画・イベント順序・非同期競合 |
| **L2** | 原典単体テスト／独立fixture | 原典ロジック自体の挙動再現 | Threadbear への接続・認可・UI動作 |
| **L3** | 模擬環境テスト（Mock Runner / 合成データ） | UI状態遷移・契約の分岐・エラー表示 | 実Runner永続化・実WebSocket・実プロセス再起動 |
| **L4** | 隔離実環境（実GPUI/実CEF + 実Runner子プロセス） | 実描画・実入力・実保存・再起動・権限拒否・隔離サンドボックス | インストール済みアプリ署名・通常更新・実配備環境 |
| **L5** | インストール版実機確認（`tb land`・更新後） | `build.json` / Git祖先一致・通常導線での実動作・実プロセス隔離 | 物理複数台構成・実配備Convex全体 |
| **L6** | 実配備・複数端末／複数Runner通し確認 | ネットワーク遅延・実同期・端末間競合・移転 | （対象要件の最高水準） |

- **件数バイアスの禁止**: 「ユニットテスト200件合格」で1件の実画面操作・実保存の未検証を覆い隠さない。
- **別機能の流用禁止**: 似た別機能（例：新規Workerスレッド作成と、既存スレッドの実行先変更）の合格証拠を流用しない。

## 2. 実条件検証マトリクス

移植した機能の種類に応じて、以下の実使用条件から該当するものを検証計画に組み込む。固定座標・英語のみ・ハッピーパスだけで検収を終えない。

| 観点 | 確認する具体条件 | よくある見逃し例 |
|---|---|---|
| **日本語・文字境界** | 日本語入力、IME変換中Enter（確定と送信の区別）、**漢字のみの入力**、絵文字・サロゲートペアの切り詰め | 漢字のみ入力の言語誤判定、IME確定で意図せず送信、文字数切り詰めで文字化け |
| **レイアウト・表示条件** | 明暗テーマ（Light/Dark）、狭いウィンドウ幅（例：Highlights併設時の1180×800）、スクロール、ウィンドウリサイズ、Retina/拡大倍率 | タブやボタンが見切れる、Retinaで切り抜き座標がずれる、パネル展開でページ本体が押し下がる |
| **操作・フォーカス・a11y** | クリック/右クリックのイベント伝播、フォーカス移動と返却順、Enter/Shift+Enter/Esc/blur、通常アニメーション有効時の連打・退場中クリック、アクセシビリティ属性 | 親パネルのメニューに吸われる、閉じた直後のクリックが捨てられる、テスト/読み上げに本文が渡らない |
| **一連のE2Eフロー** | 入口 → 選択/入力 → 確定 → 下流（チャット本文・下書き・一覧・履歴）反映 → クリック詳細/編集/削除 → 送信/実行 | 入力欄の位置だけ見て、確定後の不要バー出現やチップ化欠落を見逃す |
| **途中状態と境界変化** | 待機・確認・非同期保存の途中で「ページ遷移」「スレッド切替」「対象削除」「別操作の重ね掛け」「オフライン/再接続」を起こす | 遅れて届いた画像や応答が別スレッドに入る、古い成功応答が新しい下書きを消す |
| **永続化・再起動・競合** | Runner/アプリ再起動後の復元、同一操作IDの再送、応答消失からの再開、旧revision/旧所有世代からの変更拒否、別スコープの同一ID保護 | 再起動で関連付けや履歴が消える、同時編集で片方が黙って潰れる、他スコープのデータが混ざる |
| **権限・分離・失敗復旧** | 権限外・閉じた画面・旧leaseからの操作拒否、画像取得や外部処理が失敗してもコメント/本体を保持できるか、失敗後の再試行 | 撮影失敗で入力内容まで消える、画面クローズ後もWebパネルから更新できてしまう |

## 3. UI の時間軸比較（GUI移植時）

静止画1枚で品質を判定せず、各操作について次の時間軸を連続して確認する。

1. **開始前・開始**: 対象、選択状態、フォーカス位置、入力可否、表示位置（ページ本体がずれないか）。
2. **操作中**: 選択枠や追従UIの挙動、スクロール・リサイズ追従、他更新が入っても対象を取り違えないか。
3. **操作終了・保存待ち**: 入力保持、待機表示（二重送信防止）、旧値への一瞬の巻き戻りがないか。
4. **確定・通知・再取得**: 確定後のUI消滅、下流（チャット欄チップ・一覧・履歴等）への正確な反映、古い応答による上書き防止。
5. **拒否・失敗・結果不明**: エラー表示、入力下書きの保持、再試行手段、結果不明を成功/失敗と断定しないこと。
6. **中断・切替・再開**: キャンセル時の復元、別スレッド/別ページへ移った際のクリーンアップと再起動後の状態。

## 4. 独立レビューゲート（設計時・最終監査時）

主担当の自己確認は独立レビューに数えない。**実装前（ゲート1）** と **完了判定前（ゲート2）** の2回、別エージェントまたは独立したレビュー手段で read-only 監査を行う。

### 渡す入力（一次資料へ直接到達できる形にする）
- **ゲート1（設計レビュー）**: ユーザー依頼・合意済み範囲/対象外、既知の失敗分類、移植元の固定SHA・対象ファイル/シンボル、E2E要件対応表、全体設計（3層判定・状態所有・途中状態・失敗復旧）、Threadbear境界チェック結果、検証計画。
- **ゲート2（最終監査）**: 上記＋最新の差分・実装先、証拠レベル付きの検証結果、GUI比較・途中状態の観測記録、設計変更点、残る未確認・制約。

### レビューのルール
- 主担当が期待する結論を誘導しない。「問題がないか追認する」のではなく、**反証・欠落・劣化実装・未追跡の境界を探す**姿勢で依頼する。
- 要件対応表に載っている項目だけで閉じず、移植元の一次ソースから表自体に抜けがないかも確認させる。
- 以下の場合は、別サブエージェントだけでなく、環境で利用可能な独立高度レビュー（例：`chatgpt-pro-consult` 等、一次ソースを直接読ませて棚卸し・差分監査させる手段）を積極的に使う：
  - 移植規模が大きい（複数画面・複数モジュール・状態機械や同期を伴う）
  - 途中からの立て直し・ユーザーから「漏れがある／原典と違う」と指摘された場合
  - 移植元と Threadbear のアーキテクチャ差が大きく、UX・境界の設計判断が難しい場合

### 指摘の分類と採否
- **必須是正（完了ブロッカー）**: 合意範囲内の機能・UX欠落、根拠のない劣化簡易実装、Threadbear境界違反（パリティ/権限/互換/安全）、必須検証の不足。
- **要ユーザー判断**: 原典仕様と Threadbear 既存仕様が衝突し、どちらを採るか製品判断が必要なもの。
- **任意提案**: 動作・契約・構造要件を満たした上での改善案（採否と理由を記録）。

必須是正はすべて修正・再検証し、影響経路を再レビューで閉じてから次工程へ進む。レビュー手段が環境上どうしても使えない場合は、具体的な理由と未実施の事実を記録し、「独立レビュー済み」と偽らない。
