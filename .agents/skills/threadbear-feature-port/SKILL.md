# Threadbear 機能移植ガイド

外部アプリ・OSS・先行実装の機能を Threadbear（GPUI Desktop / CEF Webパネル / Node Runner / Convex / Web / Mobile）へ移植するとき、**「フレームワーク適応」と称した劣化簡易実装・フロー欠落・未検証のままの完了報告**を防ぐための標準手順。

維持する対象は「利用者の目的・一連の操作体験・データ契約・エッジケースを含む振る舞い」であり、単なる見た目の模倣や機能名の一致ではない。

## 守るべき5つの鉄則

1. **書き方の適応と劣化実装を分ける**
   - フレームワークや言語の違いによる構造・書き方の変更は正当だが、操作ステップ増・機能省略・エッジケース切り捨て・UX劣化を「フレームワーク差」として正当化しない。
2. **「点」ではなく一連のジャーニーで新旧比較する**
   - `入口 → 途中状態 → 確定 → 下流の表示・保存 → 再起動/再開 → 失敗・競合復旧` を1本の流れとして対応付け、一部分の動作だけで移植済みにしない。
3. **書く直前に一次ソース全文と元テストを読む**
   - 調査メモ・要約・スクリーンショット・記憶から書き起こさない。使える処理・資産は再利用を優先し、書き直す場合も分岐・境界条件・例外・後始末を原典と照合する。
4. **内部指標で完了扱いせず、勝手に範囲を削らない・止めない**
   - テスト件数、フェーズ番号、ファイル移植数を完了率にしない。未実装・未検証をユーザー合意なく「後続」「対象外」へ逃がさず、容量不足など自己回復できるブロッカーで作業を止めない。
5. **主担当の自己確認で完結させず、2回の独立レビューを通す**
   - 実装前の設計時と完了判定前の2回、主担当以外の視点から一次ソース・実経路・証拠を直接照合する。

## 工程0: 移植元の固定と既知失敗の分類

1. **比較基準を固定する**
   - 移植元リポジトリの **固定コミットSHA**（および現行 `main` との差がある場合はその区別）を特定し、手元で一次ソース全文とテストを読める状態にする。取得できない場合は読めたことにせず不足を明示する。
   - コード・資産を取り込む前に、対象版の実 `LICENSE`・`NOTICE`・個別ファイルの条件を確認し、必要な帰属・manifest 管理方針を決める。
2. **既知の失敗がある場合は先に分類する**（立て直し・漏れ是正時のみ）
   - 既存の会話での訂正・監査記録・完了撤回・不具合報告を拾い、「何が起きたか → 原因 → 検証の穴 → 予防する工程 → 検出条件」を整理する。架空の失敗は作らない。

## 工程1: 一次ソース棚卸しとE2E要件対応表（Highlights固定）

1. **利用目的と境界を確定する**
   - 依頼・合意済みの範囲・対象外・意図した仕様変更（理由と失う動作）を整理する。
   - 過去の完了報告は完了根拠にせず、検証対象として扱う。
2. **一次ソースから全動作を棚卸しする**
   - 入口（メニュー・ボタン・ショートカット・コマンド）から呼出先・状態遷移・データ形式・永続化・通知・外部作用・エラー復旧までを追う。
   - 機能名だけでなく **条件・操作・期待結果** の単位で対応表を作る：
     > `条件・操作・期待結果 → 移植元根拠 → 移植先責務 → 差分の扱い → 証拠レベル・検証方法 → 状態`
   - 複数段階の操作（選択→入力→確定→下流反映、確認→非同期実行→再取得など）は、各境界で前提が変わった場合（ページ遷移、スレッド切替、対象削除、オフライン、応答遅延・消失）の扱いも要件に含める。
3. **単一のロードマップ正本を Highlights に `pin` する**
   - [references/roadmap-template.md](references/roadmap-template.md) に沿ってロードマップ兼要件対応表を作成し、`pin`（必要なら `show: true`）でスレッドの Highlights に固定する。
   - 以降は別台帳を増やさず、この1本を更新して現在地・合意済み差分・未確認項目を常に最新に保つ。

## 工程2: 全体設計と Threadbear 固有境界の点検

最初の製品コードを変更する前に、対象全体を一つのシステムとして設計する。必ず [references/threadbear-boundaries.md](references/threadbear-boundaries.md) を一巡して以下を確定する。

1. **3層の再利用・適応方針を決める**
   - **第1層（直接再利用・抽出）**: 純ロジック、パーサー、計算、プロンプト、CSS/SVG、テストなど移植先へ依存しない部分は極力そのまま再利用・抽出する。
   - **第2層（Webパネル統合の検討）**: 複雑な原典React/HTML/CSS UIは、GPUIで劣化書き直しをする前に、既存のWebパネル等で原典部品を最小権限lease付きで安全に動かせるかも評価する。
   - **第3層（ネイティブ適応実装）**: GPUI/Rust・Runner/TS・Convexへ書き起こす場合は、原典の操作順・レイアウト・ショートカット・エッジケース・失敗時保持を落とさない設計にする。
2. **状態の正本・所有者・寿命を定める**
   - 編集中・送信待ち・確定済み・履歴の正本と所有者、非同期応答の世代照合（古い応答が新しい入力・状態を上書きしない仕組み）、中断・再起動からの復旧経路を設計する。
3. **Threadbear 固有の境界を一括点検する**
   - 4経路パリティ（本Runner / 他Runner中継 / iPhone / Web）、`docs/protocol/`、`parity.ts` / `draw-parity.ts`、権限表・Boxキー拒否、端末投影の未知フィールド非漏洩、Convex命名/API番号、ディスク形式バージョンと旧版Runner互換、macOS CEF署名・サンドボックス。
4. **未決の製品判断だけをユーザーへ確認する**
   - 仕様変更や大きな範囲縮小（一部機能を後続に回す等）が必要な場合は、失う動作と理由を示して明示的な合意を取る。合意なしで範囲を削らない。

## 工程3: 独立設計レビュー（ゲート1）

- [references/verification-and-review.md](references/verification-and-review.md) の手順に従い、実装前に主担当以外の独立レビューを受ける。
- 渡すのは主担当の要約だけでなく、**移植元の固定SHA・実ファイル参照、E2E要件対応表、全体設計、Threadbear境界チェック結果、検証計画**。
- 大規模移植・仕様が複雑な機能・抜け漏れが懸念される場合は、独立した外部調査・棚卸し（環境にある `chatgpt-pro-consult` や別エージェントの一次ソース調査）を設計段階から活用する。
- 必須指摘（合意範囲内の欠落、劣化実装のリスク、境界漏れ、検証不足）が解消するまで製品コードの実装に進まない。
- 調査・計画のみの依頼はここで終了する。

## 工程4: 原典全文参照とE2E単位での実装

1. **作業環境を正しく確保する**
   - `main` や他スレッドの worktree を直接編集しない。外部フォルダ開始のスレッドは `./borrow-worktree.sh` で作業用 worktree を借りる。
2. **書く直前に元コードを読み直す**
   - 実装する単位ごとに対象ファイル・呼び出し元・関連処理・元テストの全文を改めて読む。短く書けるという理由だけで実績ある分岐・境界条件・エラー処理を省かない。
3. **一連の利用動作を検収できる単位で実装する**
   - 「画面だけ」「APIだけ」「保存だけ」の途中段階を完了扱いにせず、入口から保存・再表示・復旧まで通る単位で組み上げる。
   - 権限境界・プロトコル定義・パリティ登録・互換ガードを後回しにせず、同じ単位で実装する。
   - 実装中に前提・契約が変わったら、局所パッチを積み上げる前に設計とロードマップを更新する。
4. **自己回復できるブロッカーで止まらない**
   - ディスク空き容量不足など、許可された手順（再生成可能なビルドキャッシュ整理や `storage-cleanup` 等）で解消できる障害は自分で回復して作業を継続する。

## 工程5: 新旧比較と実条件検収

[references/verification-and-review.md](references/verification-and-review.md) に従い、**動作**と**構造**を別々に検収する。

1. **動作の検収（新旧比較＋実条件マトリクス）**
   - 元テストが守る振る舞いを移植先の契約へ引き継ぎ、さらに Threadbear の実使用条件（日本語・IME・漢字のみ入力、明暗テーマ、狭いウィンドウ幅、Retina・リサイズ・スクロール、通常アニメーション有効、a11y、途中中断・切替・再起動・競合）を確認する。
   - GUIは静止画だけでなく、開始前 → 操作中 → 保存待ち → 確定/失敗 → 再取得/再起動の時間軸で連続確認する。
2. **構造の検収**
   - 統合後の実経路を設計と照合し、二重管理・迂回・役目を終えた暫定分岐・権限漏れが残っていないか確認する。
   - 必要な型・lint・フォーマット（`cargo fmt --all` / clippy `-D warnings`）・仕様登録・カタログ検査を通す。
3. **証拠レベルを厳密に区別して記録する**
   - 静的確認・原典単体・模擬Runner・隔離実アプリ＋実Runner・インストール版実機・実配備/複数台を混同せず、ロードマップへ正確な証拠と未確認範囲を記録する。

---

## 工程6: 独立最終監査（ゲート2）と完了判定

1. **要件と一次ソースへ戻って再監査する**
   - 修正した箇所だけでなく、要件対応表の全項目について「実装先・実経路・証拠・意図した差分」を照合する。
   - 見逃しが見つかったら、1件直すだけでなく「なぜ初回調査で漏れたか」を特定し、同じ原因が届く周辺経路をまとめて点検する。
2. **独立最終レビューを通す**
   - 主担当以外のレビューアへ最新差分・要件対応表・検証証拠・未確認事項を渡し、必須指摘をすべて是正・再検証する。
3. **厳格な完了判定**
   - 合意範囲の動作維持（または合意済み変更）、Threadbear境界の適合、必要な実条件検証、独立レビューの必須指摘解消が **すべて揃った場合のみ完了** とする。
   - 必須項目が残っているのに自己判断でターンを終わらせない。確認不能な環境制約（物理複数台・未設定端末等）がある場合のみ、代替検証と残る未確認を明確に切り分けて報告する。

## 工程7: 正式反映・更新後実機照合・後始末

1. **正式反映（`tb land`）**
   - 手動の `git merge` / `git push main` は禁止。worktree 内で `tb land`（または `runner/bin/tb land`）を実行し、標準チェックの合格と実際の `main` コミットを確認する。
   - 失敗時は回避せず原因を切り分けて修正し、再度 `tb land` を通す。
2. **通常更新後の実機照合**
   - アプリ/Runner 変更を `main` へ着地させたら、`wait_for_app_restart` を登録して自動更新を待つ（本番アプリや live runner を手動で再起動しない）。
   - 更新後、`build.json`・Git祖先関係・実プロセスの状態を照合し、可能な範囲で通常導線の動作を実機確認する（ユーザーの操作中ウィンドウや実ポインタは奪わない）。
3. **後始末とプロジェクト更新**
   - `main` 着地と確認がすべて完了してから、借りた worktree を `./borrow-worktree.sh --give-back <dir>` で返却する。
   - ロードマップを最終状態へ更新し、必要に応じて `update_project` でプロジェクト状態を最新化する。
